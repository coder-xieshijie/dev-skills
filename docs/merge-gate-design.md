# merge-gate 的来源与验证

## 从真实流程中提炼的任务

同一套“大 MR 合入前把关”的流程在 2026-10-10、10-11、10-13 手工跑了三次：在合入前的最新 head 上，由另一家模型和按领域拆分的子 Agent 交叉 review，同时在应用里跑全量功能地图，确认的问题开子 MR 修复，修完复核。每次主会话都从上一轮的材料手改四份任务说明，上一轮学到的规则在手改中丢失。

10-13 那一轮的复盘（super-auto `discussions/2026-10-14-mr7595-final-gate-retro.md`）：授权后 4 小时 41 分完成，修了 40 个定级问题、开了 11 个子 MR，没有一次等用户。失守的地方集中在一类：只写在 prompt 里、没有落到工具和输入上的约束。

- 一个审查子 Agent 跑了没隔离数据目录的单测，改写了用户的真实配置，同时在跑的地图里 92 个接口场景首跑失败；
- 派发 prompt 同时写了“全量 = 不给目标的 `run`”和“某场景不跑”，结果在真实账号里建了两个云端任务；
- 修复子 Agent 在共享仓库里用 `git stash` 做“修复前失败”的检查，5 个并行共用一个 stash 栈；
- 汇报里的数字靠手数，错了 4 次。

用户 2026-10-14 确认：做成独立 Skill；P0–P2 全修，P3 记为后续；子 MR 在 CI 通过后自动合入，主 MR 由用户合；Skill 只写流程和判断标准，平台、主机、验证手段和留存位置由运行环境、仓库和用户提供。

## 与现有 Skill 的边界

- `deliver` 是作者把需求做到可合入，merge-gate 是独立的一方在合入前把关。两者在 deliver 刚结束、head 没变时重叠，所以 merge-gate 的第 0 步先找已验证 head，只覆盖之后的变化；deliver 交付的 MR 以 deliver 的独立验证收尾，见下文 2026-10-14 一节。
- 仓库自己的验证 Skill（如 `verify-<app>`）提供实跑能力；merge-gate 不补建验证设施，缺的能力记为仓库缺口。
- `review-rules` 是审查准则；`explain-as-fool` 规定给用户的汇报；跨模型调用沿用 core-spec 的 `references/cross-model.md`；等 CI 沿用 deliver 的 `ci-watch.mjs`。
- 门禁 owner 在一个新的顶层会话里运行，不在 deliver 的会话里加载，也不当 deliver 的子 Agent：owner 决定审查范围、场景清单、子 MR 合不合、哪些问题记为被挡住，作者来做这些会偏向放行；它要派审查、裁决、修复、实跑几类子 Agent，留在顶层才不受嵌套层数限制。

## 和 deliver 接上、按审查范围定规模（2026-10-14）

### 起因

对 deliver 和 merge-gate 的对照分析（super-auto 同一讨论记录的追加部分）：

- deliver 刚结束、head 没变时再跑门禁，另一家模型的代码审查和全量实跑各重复一遍；
- 门禁改了代码后，deliver 的完成标准 2、3（另一家模型在最终 head 上 PASS、`check-delivery.mjs` 通过）不再成立，合入前还要另做一次独立验证，等于实跑三遍；
- 决定有两份：deliver 的在 plan.md 和 MR 描述顶部，门禁的在 `decisions.md` 和 MR 描述顶部的门禁一节；验证者只审 plan.md 那份；
- 交接后只有 deliver 的 owner 写分支，门禁没说什么时候接管；
- 审查领域固定 3–5 个，单模块的小改动也拉起 3 个领域。

### 用户的决定（2026-10-14）

- merge-gate 只有一个入口：合入前调用，由第 0 步决定跑多少；deliver 不在自己的会话里调用它。
- 接口（第 0 步、出口、决定清单）和规模两组改动都在 PR #41 上做，合入后安装。

### 接受的代价

- deliver 交付的 MR，每轮实跑都是另一家模型的完整独立验证，比只重跑受影响的场景贵；换来的是最终 head 上的那次验证就是 deliver 的完成记录，不再另跑一次。
- 第 0 步的“沿用”在 deliver 的报告不在本机时，只按 MR 描述里的 head 和改动的文件类型判断，比 `check-delivery.mjs` 弱。
- 目标分支前移但没有冲突、CI 通过时，第 0 步会判为不用门禁，合入后的组合代码只由平台的合并结果 pipeline 把关；用户要更强的审查时直接要求门禁。
- 两组改动在同一 PR 里一起进来（用户要求），真实效果要按上表分项观察。

### 验证

- 改前改后对照（agent-prompt-rules 4.5）：7 道情境题，覆盖只改文档和测试、目标分支前移并冲突、非 deliver 交付的 MR、deliver 交付 MR 的最终验证、换判定方法的决定、MR 仍是 Draft、单模块小改动的领域数。Claude Code 子 Agent（claude-opus-5-5，general-purpose，新上下文）和 Codex（gpt-6-astra，high，`-s read-only`）各读改前（`5984475`）和改后一次，只许读 Skill 文件。题目和四份回答存在 super-auto `discussions/2026-10-14-merge-gate-skill/probes/`。
  - 改前两家结论一致：第 1 题照跑完整门禁；第 4 题用 runtime-brief，不用 verifier brief，也不跑 `check-delivery`；第 5 题没人审替代判定方法；第 6 题“Skill 没写”；第 7 题 3 个领域、初审 4 个审查者、3 个裁决者。
  - 改后（`bb40d16`）两家 7 题都与设计一致，并引用了改后的原句：第 1 题沿用那次验证并结束，不写 `gate.md`、不改 MR 描述；第 2 题先经子 MR 合入目标分支，只审 MR 自身变化成了什么；第 4 题由另一家模型按 verifier brief 跑 verify 的全部完成判据，再跑 `check-delivery.mjs --owner`；第 5 题决定进同一份决定清单，由验证者判断是否放宽验收；第 6 题停下；第 7 题 1 个领域、初审 2 个审查者、1 个裁决者。
  - Claude 子 Agent 在第 2 题指出：只有目标分支前移并冲突、MR 自己的代码没变时，“Delta”的字面条件（验证之后代码有变化）不成立。已把 Delta 改为“有已验证 head，但代码有变化、或与目标分支冲突、或 CI 不通过”。这一处改动没有再跑一轮对照。
  - Claude 子 Agent 还指出：非 deliver 交付的 MR 上，换判定方法的决定没有验证者审，只有用户在合入前看。保留：这类 MR 通常没有冻结的验收文档。
- 链接检查、`git diff --check` 和仓库全部脚本测试通过。
- 情境题只说明文字能被读成本意，不说明门禁变快或质量没降。

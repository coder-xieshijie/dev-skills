# MR for Human：让人读懂 AI 生成代码的关键设计

本文设计一个名为 `mr-for-human` 的 Skill。它从一次 MR/PR 的实际改动出发，帮助人理解关键设计、作出取舍判断，并沿着分层说明找到真实代码。交付包括本综述、[Skill 入口](../skills/mr-for-human/SKILL.md)、按需读取的判断表、输出骨架和示例。

资料核验日期：2026-09-11。用户参考材料读取自飞书文档 revision 230 的“mr 技术分析”和“架构优化”两节。本文区分原始文献的结论、用户已有要求和本次提出的方法；方法的有效性仍需在真实阅读任务中验证。

## 1. 背景：生成和检查代码之后，人仍需要理解代码

当 AI 完成实现，又由 AI 完成 review，人容易只接触需求和问题列表。这个过程可以帮助排查缺陷，却未必让人知道：请求从哪里进入、哪些设计决定最重要、状态在哪里改变、为什么要这么做、出现异常应该到哪里定位。

逐文件阅读大 MR 的成本很高。只看摘要又会丢掉决定行为的条件、调用顺序和失败窗口。读者需要的是能够控制深度的说明：先看到少数关键决定，再理解主流程，必要时下钻到实现；每一层都能回到原代码。

这项需求与代码评审研究相符。Bacchelli 与 Bird 在 Microsoft 的实证研究发现，理解代码及其变化是现代代码评审的关键环节；评审还承担知识传递、团队认知和探索替代方案等作用。该研究发表于 2013 年，支持“理解是独立需求”，并没有直接验证生成式 AI 场景或本 Skill 的效果。[研究原文入口](https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/)

本 Skill 要解决四个具体问题：

1. 不知道重点在哪：大量局部 diff 没有告诉人哪些决定改变了系统行为。
2. 看懂局部仍串不起流程：文件、类、函数之间的协作和责任不清晰。
3. 摘要难以核实：自然语言省略了重要条件，或者解释的是理想方案。
4. 看完仍不能排查：缺少代码入口、状态观察点和可执行的验证路径。

它的验收应落在人能否解释、预测和定位，而不是摘要长度、发现 bug 数量或文档看起来是否专业。

## 2. 从参考文档继承什么

用户的[飞书参考文档](https://vrfi1sk8a0.feishu.cn/wiki/E6QPwgdYXiapkGk2yWXcLZTinih)已经提出一套有价值的阅读要求：

- 分档阅读：先理解 3 个核心点，再扩展到最多 7 个主题，最后展开全貌。
- 伪代码表达高决策密度逻辑：状态机、事务边界、不变量和安全校验。
- 保留真实标识符，为伪代码块分配稳定 ID，并映射到文件、行区间和 commit。
- 从 diff 反向核对：每个手写生产变更都有解释，或给出豁免理由；未解释部分单列。
- 将不变量与测试关联，使解释能指导定位和调试。

参考材料先提出过“1000 行伪代码”的探索，后面的精化版本改成按内容决定长度、保持简洁。本 Skill 采用后者。3 和 7 作为展示默认值保留，本版把它们归入中间层的执行逻辑拆分（见第 4 节），不把它们写成人类认知的定律，也不因此隐藏额外的重要风险。

反向核对这一条本版作了调整：保留“未展开的改动必须单列”的目的，但取消逐 hunk 编号与覆盖率计算，改为挑重点列出加五类高敏感兜底。理由和代价见第 9 节。

对于 generated、test、re-export、type-only、搬移和格式变更，本文作一项明确补充：这些是需要核实的分类，不是自动豁免。类型可能改变协议，导出可能改变公共入口，迁移或配置可能比业务代码影响更大；测试不需要进入业务伪代码，却仍可能是关键证据。

“架构优化”一节关于复用、必要改造、理解成本、owner 和回退的要求被纳入判断；其中 V1/V2 等个别 MR 的结构约束留在原场景中，不成为通用规则。

## 3. 第一性原理：先把不可回避的事实讲清楚

这里的“第一性原理”指从目标和运行约束推导判断问题。它不能代替需求调查、源码分析或实验。延迟目标、可接受数据损失、兼容窗口和团队维护成本，仍须来自具体项目。

| 基本事实或明确前提 | 推导出的设计问题 | Skill 必须产出什么 |
|---|---|---|
| 软件被使用者通过可观察行为使用 | 到底承诺了什么？完成与失败如何判定？ | 行为契约、旧/新行为及验收场景 |
| 人的注意力和上下文有限 | 哪些信息先看，哪些细节按需展开？ | 有理由的重点排序、逐层下钻与代码入口 |
| 调用者依赖暴露出来的知识 | 哪个内部变化会迫使其他模块一起改变？ | 责任边界、隐藏的决定、接口接缝及变化影响 |
| 运行依赖有限资源 | 工作量由什么放大？资源何时结束占用？ | 资源所有者、规模变量、上限和清理路径 |
| 共享状态可能被并发访问 | 哪些交错会破坏业务性质？ | 不变量、原子性/隔离机制和相应证据 |
| 跨进程、跨系统的步骤可能独立失败 | 超时、崩溃或重试后，哪些事实已成立？ | 副作用顺序、未知结果、恢复和幂等边界 |
| 部分输入和调用者不可信 | 谁能对哪个资源做什么，谁真正实施检查？ | 身份来源、信任边界和授权路径 |
| 一份解释本身也可能错误或遗漏 | 人怎样验证摘要是否忠实？ | 固定快照、正向映射、测试与未展开清单 |

由这些前提出发，可以提出一个工作准则：**重要设计必须说清它维护什么性质、依靠什么机制、证据在哪里、在什么条件下不成立。**这是本 Skill 的综合设计，不是某篇论文中的定理。

例如，“使用事务”还不足以作出判断。必须继续追到哪些读写处在同一事务里、使用什么隔离级别、远端调用是否在事务保证之外，以及冲突如何返回给调用者。

## 4. 三个分析视角与金字塔表达

顶层、中间、底层是**对同一段代码提出的三类问题**，不是三个不同的对象，也不要求项目新建 Controller/Service/Repository 三层。三者的分工可以用一句话概括：

- 顶层说：我承诺什么。
- 中间层说：我是这样一步步做的。
- 底层说：这样做依赖什么运行事实，什么条件下兑现不了承诺。

**三者对不上的地方，就是本次最重要的实现事实。**以异步导出为例：顶层承诺“已接受”，中间层显示接受时只写了一条记录，底层显示这条记录没有任何组件会消费——顶层和底层在这里对不上，这比任何单个模块的细节都更该先看。

输出组织方式是**金字塔**，不是视角与深度的交叉矩阵：

| 层次 | 内容 | 上限 |
|---|---|---|
| 第一屏 | 最核心的结论，可跨三个视角 | 5 条；明显问题无条件进，不受限制 |
| 顶层 | 功能清单、抽象清单、契约 | 按实际 |
| 中间层 | 3 个核心执行决定，扩展到最多 7 个主题，再给核心伪代码 | 3 + 7 |
| 底层 | 六项默认维度的四句式实现说明，加触发式维度 | 6 + 按需 |

早期版本把 L1/L2/L3 作为跨三个视角的阅读深度，形成 3×3 交叉。本版改为金字塔：**3+7 归入中间层**，作为执行逻辑的拆分方式；文档最前面单独保留一个可跨层的第一屏，因为最重要的事实经常是一个契约变化或一条信任边界，装不进“执行逻辑的 3 条”里。3 和 7 仍是展示默认值，不是认知定律，也不是风险上限。

每一节内部同样先给结论再展开证据。需要保留的是从行为到机制的可追溯关系。

## 5. 顶层设计：从功能承诺到模块责任

### 5.1 功能、interface、facade、seam 各解决什么

用户提到的“facade seems”，本文按 Facade 与 seams（接缝）理解。

| 概念 | 本文中的含义 | 应作出的判断 |
|---|---|---|
| 功能/用例 | 某个参与者在一定条件下获得某个结果 | 结果是什么，什么情况算失败，是否符合需求？ |
| Interface | 调用者正确使用能力必须知道的全部信息 | 除类型签名外，是否还隐藏了顺序、权限、异常和副作用要求？ |
| Facade | 向调用者提供某个子系统或用例的统一入口 | 是否减少调用者要协调的步骤和必须理解的知识？ |
| Seam | 可以替换实现或连接不同实现的边界 | 哪种实际变化可以被限制在边界内，替换后还需满足哪些契约？ |

Facade 和 seam 在此是描述设计作用的词，不强制对应某个类名。一个函数也可以提供清晰入口；一次稳定的局部调用不必为将来可能的扩展预建接口体系。

这张表在本版中**从背景依据升级为顶层的正式产出项**。顶层不再只写契约，而要交付三样东西：功能清单（谁触发 → 什么结果，含失败结果）、**抽象清单**（本次涉及的每个 interface/facade/seam 隐藏了哪个设计决定，调用者因此可以不知道什么）、契约（成功、失败、重试、取消各是什么意思）。

抽象清单有一条必须遵守的写法：**“列出本次新增的 interface”不是有效输出，因为它不做判断。**判断标准是哪种实际会发生的变化能被限制在这个边界内。如果调用者照样要知道底下的存储规则、照样要自己按顺序调多个方法，那么这个抽象没有起作用，只是让人多跳一层去读代码，应当在清单里写明这一点。

### 5.2 依据一：契约式设计

契约式设计用前置条件说明调用方的责任，用后置条件说明实现承诺，用不变量说明对象在规定边界上应维持的性质。它让“接口是什么”超出参数与返回类型。[Eiffel 官方说明](https://www.eiffel.org/doc/eiffelstudio/I2E-_Design_by_Contract_and_Assertions)

用于 MR 阅读时，提取如下信息：

| 项目 | 异步导出的教学示例 |
|---|---|
| 输入与身份 | 已认证用户、可信租户上下文、导出条件、请求标识 |
| 前置条件 | 用户有导出权限；查询条件和资源范围合法 |
| 后置条件 | 返回任务 ID 后，系统已承担哪一级别的后续处理责任？ |
| 不变量 | 任务结果只能由有权访问该租户资源的用户读取 |
| 失败与重试 | 同一请求重试会返回旧任务还是创建新任务？超时后如何查询？ |
| 取消语义 | 取消是已提交请求、已停止执行，还是已清理产物？ |

表中都是需要从需求和代码回答的问题，不能从 `Promise<Job>` 或 HTTP 202 自动推导答案。内部组件可依靠已建立的前提；不可信入口必须有真实校验，不能把安全责任写成“调用者应当诚实”。

### 5.3 依据二：信息隐藏与深模块

Parnas 的模块分解论文主张围绕应隐藏的设计决定划分模块，尤其是困难或可能变化的决定；单纯按处理步骤划分可能使同一决定散落多处。这为“按什么划边界”提供了依据。[Parnas，1972](https://doi.org/10.1145/361598.361623)

Ousterhout 将接口理解为调用者必须知道的一切，包括非形式化行为和副作用，并用“深模块”描述通过较简单接口提供较多能力的模块。它支持用调用者的知识负担判断抽象价值，而不是按方法短、类小或目录多来判定设计好坏。[作者课程讲义](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign)

在 Skill 中，检查一次具体变化：如果更换文件存储实现，API 入口、导出策略和 UI 是否都要理解新的存储规则？如果调用者仍需自行执行“创建记录、登记去重、通知任务、失败补偿”，薄 Facade 可能没有封装完整责任。

相应的好设计通常表现为：需要共同维护的不变量集中在明确责任模块，调用者依赖稳定结果；内部组织改变不会无故传播。但把所有业务集中进一个巨型服务，也可能使无关变化相互影响。判断需要看具体依赖和共同变化的原因。

### 5.4 依据三：Ports and Adapters

Cockburn 的原始文章强调，应用可以通过不同输入/输出适配器运行，领域行为能够脱离最终 UI 或数据库被驱动和测试。这支持在有实际替换需求的地方隔离技术细节。[原始文章，2005](https://alistair.cockburn.us/hexagonal-architecture)

对应到 Skill：找出真实装配点，检查替换一个 adapter 时核心判断是否保留。Mock 能测一段逻辑，并不自动证明真实 adapter 的序列化、权限和错误行为正确；这些仍需相应集成证据。

### 5.5 顶层设计的落地格式

一个重点不写成“这里用了 Facade，符合最佳实践”，而写成：

> 当前入口把权限校验、任务接受和请求去重交给同一应用操作。它减少了调用方需要协调的步骤。需要进一步核对的是：该操作返回成功时是否已经建立可恢复的执行责任。若只是存库后直接发消息，Facade 的外观并不能弥补跨系统失败窗口。

每个重点附代码位置、适用条件、一个相关替代方案和代价。只有事实能支持时才解释作者意图，否则说明这是“当前设计的效果”或“推断”。

## 6. 底层设计：从资源、时间、数据和信任推导

底层不等于只看内核、内存指针或 SQL。它指支撑功能承诺的运行事实；应用层中的缓存、Promise、事件监听器和后台任务，同样有资源和生命周期约束。

**这一节写的是“这次实现在各维度上做了什么”，不是问题清单。**问题是把实现讲清楚之后自然暴露的结论：当你写出“插入和发布是两个独立步骤，中间没有事务，也没有恢复扫描”，问题已经在读者眼前，不需要再单开一节标上“风险”。因此底层不设独立的缺陷章节，每个适用维度按四句写：

1. 这次实现做了什么：具体的读写、分配、检查，边界划在哪。
2. 它依赖什么成立：其他组件的保证、数据规模、并发度、外部系统语义。
3. 证据：文件、符号、行区间。
4. 依赖不成立会怎样——仅在依赖确实未被证明时写。

维度适用但实现没有问题时仍写前三句。“这个维度看过了，工作量是常数”本身就是全貌的一部分。说不出具体依赖条件的疑问不写进第 4 句，放入“待确认”；否则输出会退化成一批没有触发条件的“建议关注内存泄漏”，没有人能据此行动。

### 6.0 为什么是这六项

先不看任何清单，直接问：一段代码跑在真实机器上，有哪些绕不过去的事实？只有六条，每条推出一项默认必查维度。

| 不可回避的事实 | 默认必查维度 |
|---|---|
| 资源有限，拿了必须还 | 资源生命周期 |
| 工作量随输入规模增长 | 规模与容量 |
| 并发会产生交错 | 并发一致性 |
| 跨进程、跨系统的步骤会各自独立失败 | 部分失败 |
| 输入和调用者不一定可信 | 信任边界 |
| 看不见的事实没法定位 | 可观测与恢复 |

早期版本有八项，另外两项是“幂等与重试身份”和“过载与背压”。它们不多余，但**不是独立的事实**：幂等是“跨边界步骤会独立失败”的应对手段，过载是“工作量增长”与“独立失败”叠加的结果，而且在单个业务 MR 里多数不适用，除非这次改动碰了超时、重试次数、连接池或并发上限。因此本版把它们降级为触发式维度。

**时间与时钟**是本版新增的触发式维度，它是唯一用上面六条推不出来的约束：时钟是一个来自外部、不受调用方控制的输入源。墙上时钟会被 NTP 调整甚至回拨，多台机器的时钟不同步，单调时钟和墙上时钟是两回事。由此产生的超时算错、TTL 提前或永不过期、按时间戳排序在多机下乱序，都不属于上面任何一条。

**缓存、序列化与编码、迁移与部署期、不可逆操作**同样列为触发式，但理由不同：它们是已有维度的高频具体形态，不是新的第一性原理。缓存是“规模”与“并发一致性”的交叉；序列化是“不可信输入”在跨进程数据表示上的形态；迁移与部署期是“部分失败”在时间轴上的展开，特殊之处是失败窗口落在部署期间而不是单次请求内；不可逆操作属于“部分失败”，特殊之处是既不能靠重试解决也不能靠回滚代码撤销。把它们做成触发项而不是新增维度，是为了避免每个 MR 都要多回答一次“这条适不适用”——维度膨胀会让按需读取退化成全表扫描。

### 6.1 资源：谁持有，持有多少，何时释放

读取创建、使用、转移和释放的路径，至少覆盖本次相关的正常结束、异常与取消。Rust 的所有权与作用域释放提供了一个语言层面的具体实例；对其他语言应查其真实机制，不能直接套用 Rust 保证。[Rust 官方文档](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)

好的设计让资源责任可定位，例如连接由一个操作借用并在结束时归还，订阅随页面或会话销毁解除，取消信号传播到实际执行者。GC 能回收部分不再可达的内存，不会自动替业务完成关闭远端任务、删除临时文件或终止所有订阅。

Skill 输出“资源 → owner → 规模/限制 → 释放条件 → 失败时处理 → 证据”，避免停在“注意内存泄漏”。

### 6.2 性能：先算工作量，再讨论优化

设并发任务数为 c，每任务读取 n 项，每项数据本体平均 b 字节。如果所有任务同时完整持有全部项目，单看这些数据约需 c×n×b 字节。示意取 c=8、n=100,000、b=1 KiB，数据本体约 781 MiB；对象和缓冲开销尚未计入。

这个估算揭示需要查明的条件：数据是否全量加载、是否复制、是否流式传递、并发是否有上限。它没有证明真实内存峰值，也不能据此虚构优化后的性能。改成分批处理后，只有下游也不累积全部结果，内存才可能受批大小约束。

对数据访问同样检查查询次数、扫描范围、索引适用性和批处理：n 个对象逐个远端获取会放大请求数；一次批量获取又可能增加单批内存与尾延迟。好的选择取决于实际规模和服务预算。

Google SRE 的级联故障讨论说明，资源耗尽会增加在途请求，重试又可能放大负载。它支持将队列长度、等待期限和重试策略一并分析，而非仅看正常路径耗时。[Google SRE](https://sre.google/sre-book/addressing-cascading-failures/)

### 6.3 数据与并发：不变量在哪里成为事实

先写业务性质，再寻找实施位置。例如“同一租户、同一幂等键只对应一个请求结果”，需要检查键的作用域、唯一约束或条件写入，以及读取后再写入的竞争窗口。

“放进事务”不是完整答案。PostgreSQL 的不同隔离级别有不同的可见性和异常语义，Serializable 也需要处理序列化失败；应用要按实际版本和配置判断。[PostgreSQL 14 事务隔离文档](https://www.postgresql.org/docs/14/transaction-iso.html)

好的设计把决定性的约束放在能保护实际并发范围的位置。进程内锁可以解决进程内竞争，却不能自行约束其他进程；数据库唯一约束能约束对应数据，却不能自动确保消息已经投递。

### 6.4 部分失败：返回、持久化和交付是不同事实

分析每两个副作用之间的失败窗口。例如：

```text
写入 job 记录
向 broker 发布消息
向调用者返回任务 ID
```

若在第一步后失败，记录可能存在而消息不存在；若消息已接收而响应丢失，调用者会面临结果不确定。是否需要 outbox、重试、查询确认或人工恢复，要由本次承诺和现有机制决定。

AWS 的幂等 API 文章强调请求身份、同键不同意图、语义等价响应，以及去重记录与相应变更的原子性。它为安全重试提供具体判断依据，但并不赋予任意跨系统流程端到端 exactly-once 保证。[AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

Outbox 是一个可选设计：在同一数据库事务内保存业务状态与待发送事件，由后续发送器交付。它解决的是特定的库内记录与待交付意图一致性问题；发送器仍可能重复投递，需要消费端语义、积压限制、恢复与监控。一个允许用户重新发起、没有可靠交付承诺的轻量操作未必值得引入这些机制。

### 6.5 安全：检查真正发生在什么边界

Saltzer 与 Schroeder 提出的机制简洁、默认拒绝、完整仲裁和最小权限，为检查授权路径提供了基础。作者也明确说明这些原则是帮助发现潜在问题的指引，不能机械当成无条件规则。[原始论文的原则章节](https://www.mit.edu/~Saltzer/publications/protection/Basic.html)

Skill 要追到“已认证的谁，对哪个资源，在什么执行身份下，做哪种操作”，再看后台任务、恢复、重试和替代入口是否使用同样的授权语义。按钮被禁用、请求中出现 tenantId、类型名叫 SafeRequest，都不能单独作为授权已经实施的证据。

一个好的设计可以复用可信入口的结果，但需要说明结果的作用域、有效期及权限变动后的处理。对权限检查缓存，重点是能否证明每次实际访问仍受有效权限约束，而不是无条件要求所有层重复查询。

### 6.6 回退与观察

人要排查问题，就必须分辨“执行了”“持久化了”“通知了”“UI 显示了”。统一的请求/任务标识、能反映事实的状态和合适的日志，可以帮助定位责任层。

同样，回退代码不自动回退已写数据或已触发的外部副作用。涉及持久化格式、迁移或不可逆操作时，Skill 应明确代码回退和数据恢复的边界；若不涉及，简单说明即可。

## 7. 中间逻辑：用逐步细化连接承诺与实现

Dijkstra 的逐步细化展示了如何用不同抽象层次组织程序理解：一层可以在假定下一层提供所需能力的条件下被理解。用于这里时，关键是下层展开仍维持上层陈述的含义。[Notes on Structured Programming](https://www.cs.utexas.edu/~EWD/transcriptions/EWD02xx/EWD249/EWD249.html)

本 Skill 采用以下表达方式：

- 第一屏说清决定：例如“重复请求返回同一任务”。
- 中间层解释机制：从可信身份得到租户，在查重后决定返回或创建。
- 伪代码与底层展开实际条件、读写顺序、状态、异常和清理，再定位到源代码。

伪代码块用 P01 等稳定 ID；不变量用 I01 等 ID。稳定意味着同一语义在文档修订中尽量沿用 ID，不意味着代码改变后映射可以不重算。

伪代码可以省略语法细节，但以下内容一旦改变行为就必须保留：

| 必须保留 | 省略后的风险 |
|---|---|
| 身份来源、关键条件和错误码 | 把不可信输入当成可信前提，或隐藏拒绝语义 |
| 状态转换与旧状态检查 | 掩盖非法转换或重复执行 |
| 等待、并发与提交范围 | 将多步动作误述为顺序或原子操作 |
| 外部调用和失败处理 | 隐藏数据已写、外部动作未完成的窗口 |
| 取消和清理条件 | 误以为停止等待等于停止工作 |

可直接查看[完整教学示例](../skills/mr-for-human/references/worked-example.md)：它从一段简短实现推导三层说明，保留发布失败窗口，并同时指出已成立的租户隔离设计。示例是合成材料，用来说明输出形式，不代表某个真实 MR。

## 8. 如何决定“值得人重点看”

重点的单位是实现选择或行为变化，而非文件、代码行数或缺陷条目。选择前先扫描所有改动，再追调用和影响。

主判据只有一条：**改掉这个实现选择，功能的行为或保证会不会变。**拆成四个可当场判断的方向：

| 重要性判据 | 含义 | 例子 |
|---|---|---|
| 承载承诺 | 功能对外说的某句话，是靠这段代码兑现的 | “重试返回原任务”靠的就是那三行查重 |
| 划定边界 | 事务范围、并发范围、信任边界、资源生命周期的起止 | 权限检查放在业务读写之前还是之后 |
| 被复用 | 改一处影响多处 | 共享默认值、公共协议、公共工具函数 |
| 建立新约束 | 之后的代码都要遵守它 | 新状态、新存储、新的异步边界 |

下面两项影响**展开方式**，不单独构成重要性：理解难度（跨模块调用、隐式顺序、错误恢复）决定要不要给分层链路和定位点；证据缺口（描述与代码冲突、无相关断言、依赖实现不可见）决定要不要保留为未决重点并标明边界。

第一屏的排序按分档，不打分：

1. 已证明的错误，后果不可逆——数据错乱、权限绕过、扣错钱、误删。
2. 已证明的错误，后果可恢复。
3. 未证实的风险，后果不可逆**或不可观测**。
4. 未证实的风险，后果可恢复——性能退化、资源占用。
5. 可维护性与理解成本。

同档内按触发条件有多容易满足排：默认配置下就会发生 > 需要特定规模或并发 > 需要罕见的失败时序。第 3 档把“不可观测”与“不可逆”并列，理由是如果一件事出了问题没人知道它出了问题，它比会报警的故障更危险——没有人会去修。

“明显问题”与“潜在风险”的区别不是严重程度，而是**能不能拿出反例**：明显问题能构造具体输入或时序证明结果违反契约，读者该改代码；潜在风险的实现自身自洽，但依赖一个尚未证实成立的条件，读者要先去确认那个条件。两者都拿不出的，属于“待确认”，不能混进重点。

这里没有人为制造一个“风险分数”。缺少校准数据时，将主观数字相乘只会产生虚假的精确感。每个重点用一句具体理由说明入选并说明为什么排在这个位置；“先读”也不等于“有 bug”。

金字塔结构最大的失败模式不是写得不够全，而是**第一屏那几条选错了**：选错之后下面写得再完整也没用，因为读者只读最前面。重点选择目前没有客观标准，唯一的缓解办法就是要求每条写出排序理由，把判断权交还给读者，使他能自行检查这个排序是否成立。

其余变更放进“未展开的改动”清单，见第 9 节。

## 9. 代码定位与遗漏控制

正向映射解决“这句话依据在哪里”：

```text
设计决定 D01 / 伪代码 P01 / 不变量 I01
    → 文件、符号、行区间、base 或 head SHA
    → 可定位链接、测试断言、运行状态
```

**这一项不省略。**伪代码的唯一价值是忠实于实现，不能核对就不如不写。

### 9.1 为什么放弃全量反向账本

早期版本要求给每个 diff hunk 分配 ID，指向解释块或写出豁免理由，并按 H=E+X+U 报告记账覆盖率 (E+X)/H 与映射率 E/(H-X)。本版取消这套记账，原因有两条：

- **成本与 diff 规模成正比。**逐块编号、填表、算比率的工作量随改动量线性增长，而这部分内容对读者理解实现没有贡献。
- **数字的信息量很低。**覆盖率只说明“有没有记账”，不说明代码是否正确。教学示例正是为此保留的：它的 H=1、E=1，两个比例都是 100%，但不变量 I03 并不成立。

### 9.2 代价与补偿

取消的代价必须写清：反向账本原本是**唯一能回答“这份文档有没有漏讲某块改动”的机制**。取消之后，保证边界从“逐块记账、漏了必然被发现”降级为“已扫描全部改动并主动列出被判为次要的高敏感项”。

具体风险是这样的：几个核心决定写得非常准确、伪代码也忠实，但 MR 里还有一处把默认超时从 30 秒改成 3 秒，没人提到它，而且没有任何地方会让读者发现它被漏掉。

补偿办法是一个低成本的兜底清单。“未展开的改动”按文件或符号粒度挑重点列出，每条一句话说明为什么次要；下面五类**即使判断为次要也必须列出**：

权限相关、配置与默认值、数据库迁移、协议/IDL 定义、共享工具函数。

这五类的共同特点是改动行数少但影响面大，正是“抓大放小”最容易误伤的位置。兜底的成本是清单里多几行字。

### 9.3 证据分级

证据同时分两条轴记录：

| 主张来源 | 验证状态 |
|---|---|
| 已确认需求、代码事实、推断、未知 | 静态核实、有测试未运行、已运行及结果、未验证 |

例如，“源码确实先写后发”可以是代码事实、静态核实；“线上会丢任务”仍需具体失败条件和恢复机制证据。测试文件存在与测试相关、相关与已经执行、已经执行与覆盖真实生产环境，均应分开。

## 10. Skill 的执行流程与完成条件

| 阶段 | Agent 做什么 | 何时算完成 |
|---|---|---|
| 固定对象 | 确认需求、base/head、差异范围与材料完整性 | 能明确说出分析快照与证据边界 |
| 重建行为 | 对照旧/新实现，追正常和关键失败路径 | 从触发到结果每一段有来源或未知标记 |
| 选择重点 | 扫全部变更，按后果与理解需要排序 | 每个重点有入选理由，其余变更有账 |
| 三视角分析 | 从契约追到逻辑、资源、数据和权限实施点 | 重要承诺能定位机制，不成立之处显式列出 |
| 分层表达 | 写第一屏、中间层 3+7、伪代码和不变量 | 下层展开保持上层行为语义 |
| 定位核验 | 正向映射、未展开清单、核实位置与测试状态 | 高敏感类别已逐类核对，未展开项可查 |
| 人的阅读路线 | 给代码打开顺序、观察值和验证入口 | 能回答为什么、失败后怎样、到哪里定位 |
| 交付 | 回读 head，说明静态/执行结果及缺口 | 读者得到可独立使用的完整指南 |

正常情况下 Agent 直接查可查的信息。需求意图无法确定时注明假设并提出必要问题；工具不可访问时交付已知部分及具体缺口。不会把所有未知都退回给人，也不会编造不可见实现。

大 MR 可以按行为簇分批下钻，但使用同一份快照和总账；省略的批次要显式标注。用户限定某目录时，在限定范围内完整记账，对必要的跨范围依赖只解释其契约及已知影响。

## 11. 好的软件设计如何体现在输出里

以下是条件性设计判断，不是要求每个项目采用的模式清单。

| 场景 | 值得解释的好设计 | 收益 | 代价及适用边界 |
|---|---|---|---|
| 多个入口触发同一业务规则 | 完整应用操作封装共同决策 | 调用者少协调，规则责任清楚 | 需保持用例边界，避免统一入口膨胀 |
| 外部存储实现确有替换需要 | 在稳定领域语义上设 port/adapter | 内部替换影响局部化，可独立测试 | 额外接口和装配成本，仍需真实 adapter 验证 |
| 并发提交需保持唯一性 | 合适范围的唯一约束或条件更新 | 让决定性约束靠近共享状态 | 冲突处理及数据库语义需要核实 |
| 必须可靠接受跨系统任务 | 事务记录业务事实与待发送意图 | 降低记录存在却无交付意图的窗口 | 重复投递、积压、恢复和消费语义仍有成本 |
| 大结果集和有限内存 | 有界批次与端到端流式消费 | 工作集更可控 | 吞吐、排序、一致性和重试更复杂 |
| 长生命周期会话或页面 | 资源拥有者和清理边界明确 | 泄漏和后台工作更易定位 | 取消传播与异步清理要验证 |
| 多租户或后台执行 | 可信身份传递到实际资源访问 | 授权行为可追溯 | 缓存授权和权限变更需明确定义 |

选择替代方案时先寻找项目已有能力。能够通过已有任务系统的恢复扫描满足承诺，就不应因为看到“先写后发”立即建议再造 outbox。成立的缺陷必须在实际调用链与故障条件下证明。

## 12. 输出给人看起来是什么

一次完整运行通常交付一个主 Markdown 文档，大型清单可以单独放附件并从正文链接。建议顺序是：

1. 对象、快照、需求和一句话行为变化。
2. 第一屏：最多 5 条跨层结论，每条带类型与排序理由；明显问题无条件进。
3. 顶层：功能清单、抽象清单、契约。
4. 中间层：3 个核心执行决定扩展到最多 7 个主题，正常/失败主链路，必要时配一张图，再给核心伪代码。
5. 底层：六项默认维度的四句式实现说明，加触发式维度与重点卡片。
6. 正向映射与未展开的改动清单。
7. 待确认事项。
8. 人的阅读路线、调试入口、验证结果与缺口。

每个重点卡片有稳定问题和证据。例如“已有记录的重试为什么可能跳过发布”，比“任务模块分析”更能指导读者。

交付不应依赖聊天历史。只有已读取的文件/符号/行号可作为证据；链接的版本与解释快照保持一致。head 变化后，原文仍可作为旧快照指南，但不能继续称为最新。

## 13. 它与现有 Skills 的关系

本次核对了仓库现有入口，分工如下：

| Skill | 核心任务 | 与本 Skill 的关系 |
|---|---|---|
| `design-for-review` | 从需求和设计材料整理待评审技术方案 | 更侧重拟定方案；本 Skill 从实际 diff 还原实现 |
| `review-rules` | 判断正确性、必要改造、复杂度与责任边界 | 可以提供评判标准；本 Skill 增加分层理解与证据导航 |
| `explain-as-fool` | 面向无背景读者清楚表达 | 表达目标相容，不承担 MR 清单与源码映射 |
| `mr-for-human` | 带人理解改动并能追到关键实现 | 可在阅读、评审准备、交接和开始排查前使用 |

新 Skill 不把这些现有 Skill 设为强制依赖。关键执行指引自包含，适合从完整 Skill 目录加载；综述用于解释设计依据，不要求每次运行全文读入。

## 14. 预期好处与验证方式

预期收益是缩短建立心智模型和定位证据的时间，同时保留人作设计判断的能力。此处是待验证假设，没有实测收益百分比。

| 期望改善 | 可观察验证 |
|---|---|
| 更快找到重要决定 | 记录从开始阅读到指出关键入口、状态 owner 和主要取舍的耗时 |
| 理解更准确 | 给定正常与失败输入，检查读者对行为的预测能否与代码/实验一致 |
| 更易定位 | 给一个相关症状，记录定位到责任函数及证据的时间 |
| 摘要更可信 | 抽查重点、伪代码与源代码是否一致，核实未展开清单与五类高敏感兜底 |
| 保持人工判断 | 读者能说明替代方案为何合适或不合适，而非重复模式名称 |

建议后续挑选规模相近的真实 MR，交替使用普通 diff/摘要与阅读指南；保持背景材料相当，记录时间、答案正确性、需要补充的上下文。重复阅读同一 MR 会带来学习效应，应在比较时记录或避免。不能用文档作者自己觉得清楚来替代读者效果。

这次交付的结构验证、场景核验和边界记录在[验证记录](mr-for-human-validation.md)。其结论只适用于实际完成的检查；尚未验证长期收益、多人使用或不同 Agent 的稳定表现。

### 15.1 本轮修订（金字塔结构与底层收敛）

在同一分支上对初版作三处结构性调整，依据是与用户的设计讨论：

- **顶层**增加功能清单与抽象清单（interface/facade/seam 各隐藏了哪个设计决定），不再只写契约。
- **底层**从八项平铺维度收敛为六项默认必查加七项触发式，且输出格式从检查项改为四句式实现说明；新增“时间与时钟”触发式维度。这一节的定位是说明实现是什么样，不是列问题清单。
- **组织方式**改为金字塔：3+7 归入中间层，文档最前面是可跨层的第一屏（最多 5 条，明显问题无条件进）；取消逐 hunk 反向账本与覆盖率计算，改为“未展开的改动”挑重点清单加五类高敏感兜底。

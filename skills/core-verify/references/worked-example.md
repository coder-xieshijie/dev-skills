# 示例：执行额度改造的验收要求

以下沿用 core-spec 示例中的“执行额度改造”spec，脱敏简化，用于说明证明方式、断言松紧和错误实现的写法；其中业务规则不适用于其他任务。

## 输入：spec 中的规范性内容

- 额度按实际发出的逻辑请求计数：同一请求内部重试不额外计数；发送前被拦截不计数；发出后失败仍计数。
- 旧额度原数延续：旧上限 12、已用 7 → 新上限 12、历史占用 7、剩余 5；历史部分标注旧口径。
- 额度用尽拦截下一次普通请求；最后一次获准请求的结果仍被处理；时间、权限和用户停止仍可独立阻止后续执行。
- 只在当前执行仍可继续时收尾，不为总结新建执行；接受部分停止场景没有新总结。

## 可以形成的 verify 片段

### 要求表

| ID | 要求 | spec 位置 | 证明方式 |
|---|---|---|---|
| R01 | 同一请求内部重试，计数只加 1 | 按逻辑请求计数 | 场景 S01 |
| R02 | 发送前被拦截的请求不计数 | 按逻辑请求计数 | 场景 S01 |
| R03 | 发出后失败的请求仍计数 | 按逻辑请求计数 | 场景 S01 |
| R04 | 旧数据升级后剩余 5 次，历史 7 次标注旧口径 | 保留历史额度 | 场景 S03 |
| R05 | 额度用尽后，下一次普通请求不发出 | 最后一次获准请求 | 场景 S02 |
| R06 | 最后一次获准请求的结果仍被处理 | 最后一次获准请求 | 场景 S02 |
| R07 | 没有可继续的当前执行时不新建执行，保留已有结果和停止状态 | 当前执行可以继续时才收尾 | 场景 S04 |

### 场景

```text
S01 计数规则　覆盖：R01、R02、R03　层次：集成　必需
入口：任务执行接口
前提：用测试数据把剩余额度设为 5；外部 provider 用替身，可控制首次失败后重试成功、发送前拦截、发出后失败
操作：依次触发三种情况
必须观察到：计数分别为 +1、+0、+1；剩余额度读回为 3
不得出现：重试让计数 +2；被拦截的请求计数
基线预期：失败（旧口径不按逻辑请求计数）
错误实现：每次 HTTP 尝试都计数（重试后计数 +2）；在发送前就计数（被拦截的也 +1）
观察方式与证据：额度查询结果、替身收到的请求记录
执行状态：需补观察工具（缺口 G1）
```

```text
S02 用尽边界　覆盖：R05、R06　层次：真实入口　必需
入口：界面发起任务；CLI 发起任务
前提：用测试数据把剩余额度设为 1
操作：从两个入口分别发起任务，第一次请求获准并返回结果
必须观察到：该结果出现在执行记录中；实际发出的逻辑请求数为 1
不得出现：第二次普通请求发出
基线预期：失败（基线在额度归零时立即终止，结果未进入执行记录）
错误实现：结果返回后才检查额度（第二次请求已发出）
观察方式与证据：执行记录、出站请求记录
执行状态：实现后绑定命令
```

S03、S04 按同样字段书写，此处省略。

## 检查案例与判断

以下是独立的检查情境，每行给出候选写法及应作的判断。

| 候选写法 | 判断与最小处置 |
|---|---|
| S02 只断言“界面显示剩余 0” | 太松。“结果返回后才检查额度”的错误实现同样显示 0；改为断言实际出站请求数 |
| S02 的正向观察删掉，只留“不得出现第二次请求” | 太松。实现什么都不做也不会发第二次请求；保留“第一次结果进入执行记录”作为正向观察 |
| S01 的预期写成“剩余额度等于 `quota.remaining()` 的返回值” | 自引用。预期取自被测代码，错误实现也会通过；改为 spec 推出的字面值 3 |
| S01 基线预期写成“通过” | 矛盾。计数口径在本次改变，场景在旧代码上通过说明它没测到改变；重查断言 |
| S02 只从 CLI 发起任务 | 不完整。同一行为也能从界面触发，一个入口的结果不代表另一个；补界面入口或写明不需要的依据 |
| 为验证 R06，直接调用内部的结果处理函数 | 不走用户路径。剩余额度可以用测试数据安排，被验证的“结果被处理”必须由入口发起的真实任务产生 |
| S01 断言“`RequestLedger.increment` 被调用一次” | 太窄。spec 没有指定内部结构，其他正确实现会被误拒；改为断言对外可见的计数结果 |
| 为 R04 增加“迁移 5 秒内完成” | 越界。spec 没有时间要求，删除 |
| spec 未说明两个并发执行共享额度时最后一次名额归谁，草稿写成“先发起者获得” | 不能自行补定。向用户提问，答复写进 spec 后再写场景；答复前标为待确认 |
| 接受的代价“部分停止场景没有新总结”没有对应要求 | 遗漏。接受的代价也是约定，需要场景确认此时不新建执行，防止实现为补总结而新建执行 |
| S01 用 provider 替身 | 可以。计数发生在本系统内，替身只替代外部响应；spec 要求真实 provider 行为时不能这样替代 |
| R01–R03 各写一个真实入口场景 | 不必要。一个集成场景能覆盖三条计数规则；真实入口留给 S02 这类跨模块路径 |
| “复用现有额度存储，不新增表”写成场景 | 证明方式不对。这是结构性约束，改为评审检查，写明检查什么、怎样算不通过 |

仅在实际完成这些核对后给出结论，不照抄示例中的场景或判断。

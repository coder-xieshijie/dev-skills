# 依据 spec 产出验收文档

交付一份可独立阅读的中文 Markdown《<主题>：验收要求》，默认文件名 `verify.md`。读者据此判断：一个实现怎样才算满足 spec，要在哪里观察什么结果、留下什么证据，才能宣布完成。

这份文档在写 plan 和代码之前完成，验收依据只来自 spec，计划和实现中的遗漏因此不会缩小验收范围。它规定验什么、怎样判定；实现步骤、测试代码和执行结果不在其中。

## 1. 以 spec 为唯一依据

还没有 spec 时，先读取并按 [core-spec 的正文规则](../core-spec/SKILL.md) 从当前会话和材料生成 spec，再继续。这里直接读取同仓库文件，core-spec 的手动触发设置不变。

读取 spec 全文，记录路径、内容 sha256 和相关仓库的当前 commit。spec 是需求的唯一来源。当前会话、ADR 和术语表用于理解 spec 的用词、找具体例子；要求只从 spec 来。

逐条列出 spec 中的规范性内容：选定的行为、默认值、条件与例外、不得发生的事、必须保持的现有行为、接受的代价和不变量。只解释理由的句子不列。

写验收常会暴露 spec 没有定下的行为，例如取消后是否继续、并发时谁先获得资源。会改变判定结果的，同样按 core-spec 更新 spec：它从会话中找出最终约定，仍未确定时向用户提出最小必要问题。spec 更新并重新记录哈希后，再写对应验收；更新之前，相关要求标为待确认，其余部分继续。只影响实现方式、不影响判定的，留给实现。

完成条件：spec 的每条规范性内容都有去处，成为一条要求，或并入另一条要求并注明。

## 2. 把约定写成可判断的要求

每条要求给一个稳定 ID（R01、R02……），写成可观察的结论，并注明 spec 位置。一条约定带多个条件或例外时拆开，让每个例外都能单独判定。

为每条要求选定证明方式：

| 证明方式 | 适用内容 |
|---|---|
| 场景 | 行为、状态、输出、副作用 |
| 评审或静态检查 | 结构性约束，例如复用指定能力、不新增依赖、接口保持兼容；写明检查什么、怎样算不通过 |
| 已有检查 | 仓库现有测试、类型检查或 lint 已能证明的部分；写明具体文件或命令 |

完成条件：每条要求都有证明方式，读者无需猜测怎样判定。

## 3. 为行为要求设计场景

每个场景按以下字段写：

```text
S01 <标题>　覆盖：R01、R03　层次：单测 / 集成 / 真实入口　必需或可选
前提：
操作：从哪个入口、做什么
必须观察到：
不得出现：
观察方式与证据：
错误实现：一个看似合理、会让本场景失败的做法
执行状态：入口已存在 / 需补观察工具（见工具缺口）/ 实现后绑定命令
```

- **按风险选最少且足够的层次。** 局部规则用单测；模块接线和默认装配用集成检查；用户可见流程、跨模块路径和 spec 点名的真实环境用真实入口。一个场景可以覆盖多条要求；关键例外单独成场景。
- **观察实际结果。** 断言落在实际发出的参数、持久化后的状态、默认启动下的装配和最终副作用上。界面显示、函数被调用、日志出现只作辅助证据。
- **写出错误实现。** 每个必需场景给出一个看似合理、却违反所覆盖要求的实现，并确认断言会让它失败。找不到会被拒绝的错误实现，说明断言太松。
- **只约束 spec 约定的内容。** 断言检查 spec 要求的结果。spec 没有指定的内部结构、命名和实现路径不进断言，其他正确实现应当能通过。
- **mock 只证明它边界内的行为。** spec 要求真实 provider、真实设备或真实入口时，mock 场景不能替代。
- **无法用代码断言的结果**，如模型输出质量或视觉效果，写明固定样本、参照和判定标准，并注明需要独立判断。

完成条件：每条场景型要求至少有一个必需场景；每个必需场景都有会被它拒绝的错误实现。

## 4. 定位入口，列出工具缺口

在当前代码中为每个场景找入口和观察手段：已有测试、CLI、API、日志、调试接口、数据查询。引用的入口必须在当前 commit 中存在；能低成本试运行的，试运行一次。

本次才实现的功能，写明入口类型和观察方式，具体命令留到实现后的验收时绑定。尚未确定的命令、参数和路径，按“实现后绑定命令”标注。

现在观察不到、需要先补的能力（例如看不到实际发出的请求），列入“验证工具缺口”：缺什么、服务哪些场景。plan 会把这些排在功能实现之前。

完成条件：每个必需场景的执行状态如实标注，每个缺口都对应到场景。

## 5. 写成文档，对照 spec 核对

文档依次包含：

1. **用途与效力**，可按主题调整：

   > 本文依据 spec 规定本次需求怎样算做对、如何证明，是 plan 编写、交叉评审、实现和最终验收的共同依据。本文只描述验收要求，不代表验证已经执行或通过。

   随后写来源：spec 路径与 sha256，相关仓库与 commit。
2. **重点**：要求数、必需场景数，以及 3–5 个最容易出错的场景，通常是跨模块真实路径、默认装配和关键例外，一屏内看清。
3. **要求表**：ID、要求、spec 位置、证明方式。
4. **场景**。
5. **回归范围**：本次改动触及、spec 没有要求改变的现有行为，用仓库已有测试或补充场景覆盖。spec 明确改变的行为，旧测试随之更新，不算回归。
6. **验证工具缺口**。
7. **完成条件**：全部必需场景在交付版本上通过，证据对应该版本的代码和运行实例。

交付前对照 spec 核对：

- **spec → verify：** 每条规范性内容都有要求和证明方式；默认值、例外和不得发生的事没有在合并时丢失。
- **verify → spec：** 没有 spec 以外的要求、阈值或语义。
- **判别力：** 逐个必需场景确认列出的错误实现会失败；没有只检查界面或内部调用的断言。
- **执行状态：** 未定位的入口和尚未确定的命令已如实标注。

判断断言松紧、证明方式或错误实现写法时，读取[示例与检查案例](references/worked-example.md)。

默认交付一个 `verify.md`，与 spec 放在同一目录，或使用用户指定路径。最终回复给出文件链接、要求数与必需场景数、工具缺口和仍待确认的问题。产出 verify.md 不包含编写测试代码、执行验证或启动其他 agent。

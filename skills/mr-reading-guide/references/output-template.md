# 阅读指南输出骨架

这是可裁剪的 Markdown 骨架，按金字塔组织：最核心的内容在最前面，逐步展开。正文讲实现与决定，表格承载证据。简单变更合并章节，相关的重点才使用详细卡片。

## 0. 对象与快照

- 分析对象、需求来源、base/head、获取时间；本地差异另写快照标识。
- diff 是否完整，阅读/运行范围，已知缺口；已确认需求和当前实现的差异。
- 一句话描述触发场景以及旧行为 → 新行为。

## 1. 第一屏：先看这些

最多 5 条，可以跨三个视角。明显问题无条件进，不受条数限制。每条一行：

```
【类型】一句结论 — 文件:行号
  为什么排在这里：一句理由
```

类型只有三种：**明显问题**（拿得出反例，读者该改代码）、**潜在风险**（拿得出触发条件，读者先去确认那个条件）、**核心决定**（实现成立的关键选择）。

排序按分档，不打分：已证明且后果不可逆 > 已证明且后果可恢复 > 未证实但后果不可逆或不可观测 > 未证实且后果可恢复 > 可维护性。同档内按触发条件有多容易满足排。

## 2. 顶层：功能、抽象与契约

### 功能清单

| 参与者与触发 | 条件 | 成功结果 | 失败/拒绝/取消各产生什么 | 证据 |
|---|---|---|---|---|

### 抽象清单

| 抽象（interface/facade/seam） | 隐藏了哪个设计决定 | 调用者因此不必知道什么 | 哪种实际变化被限制在边界内 | 证据 |
|---|---|---|---|---|

判断标准不是有没有定义接口。仍要求调用者自行按顺序协调多步、或仍泄漏同样的内部细节时，写明这一点。

### 行为契约

| 操作/参与者 | 输入与前提 | 结果及后置条件 | 失败/取消/重试 | 责任模块与证据 |
|---|---|---|---|---|

## 3. 中间层：执行逻辑

先 3 个核心执行决定，再扩展到最多 7 个主题，按行为顺序连接。

用文字、伪代码或一张必要的流程/时序/状态图表达入口、参与者、关键数据变化、结果和相关失败。图可用 Mermaid；图里的每条实线关系必须有实现证据，推断与提议明确区分。

### 核心伪代码

每块 P01、P02……保留实际标识符与关键顺序。标明属于当前实现还是建议方案。不把多步动作写成代码并未提供的原子操作。

### 不变量与验证

| ID | 要维持的性质及来源 | 实施机制/代码 | 测试与具体断言 | 验证状态/缺口 |
|---|---|---|---|---|

没有测试时写明缺失。测试文件存在、断言相关、已经执行通过分别说明。

## 4. 底层：实现所依赖的运行事实

这一节写实现是什么样，不是问题清单。六项默认必查：**资源生命周期 / 规模与容量 / 并发一致性 / 部分失败 / 信任边界 / 可观测与恢复**。触发式维度按 [design-lenses.md](design-lenses.md) 取用。

每个适用维度按四句写：

**维度名**

1. 这次实现做了什么：具体的读写、分配、检查，边界划在哪。
2. 它依赖什么成立。
3. 证据：文件、符号、行区间。
4. 依赖不成立会怎样 —— 仅在依赖确实未被证明时写。

维度适用但实现没有问题时，仍写前三句。与本次无关的维度一句依据裁剪。说不出具体依赖条件的疑问不写进第 4 句，放入第 6 节。

### 重点卡片

只对确有取舍的重点使用：

**D01 — 一个可以回答的设计问题**

- 当前选择、责任模块、适用条件。
- 原理 → 本次代码事实 → 判断；事实/需求/推断/未知分开。
- 已复用能力；相关替代方案、收益、代价和何时值得改。
- 原代码位置、P/I 引用、验证状态、剩余缺口。

## 5. 代码定位与未展开的改动

### 正向映射

| 解释 ID | 文件/符号 | base 或 head 的行区间 | 快照 SHA | 定位链接 |
|---|---|---|---|---|

行区间是文字字段；链接指向实际起始行。删除逻辑引用 base。一个解释块对应多处实现时列齐；必要的未改调用方标为“上下文”。这一项不省略——伪代码的价值是忠实，不能核对就不如不写。

### 未展开的改动

| 位置（文件或符号） | 变化内容 | 为什么次要 |
|---|---|---|

下面五类即使判断为次要也必须列出：**权限相关、配置与默认值、数据库迁移、协议/IDL 定义、共享工具函数**。它们改动行数少但影响面大。

保证边界写明：这是“已扫描全部改动并主动列出被判为次要的高敏感项”，不是“逐块记账、漏了必然被发现”。

## 6. 待确认

- 说不出具体依赖条件的疑问。
- 需要人决定的业务取舍，以及需要运行才能回答的问题及最小验证动作。

## 7. 阅读与排查路线

给出按顺序打开的少数位置，以及每一步要看什么。例如：

“从入口看 actor 和请求 ID；到决策函数看是否进入拒绝分支；到存储看提交结果；到通知层看发送状态；最后看 UI 用了哪个状态字段。”

具体函数、日志、运行与测试命令取自实际仓库。说明预期值与能推翻解释的观察结果。

## 8. 验证边界

- 静态已核实的链路与引用。
- 实际运行的命令、快照、结果及适用范围。
- 未展开的改动、待验证主张、需要人决定的业务取舍。
- 交付前 head 回读结果；过时则显式注明。

最后用具体场景写出“为什么这样设计 / 某次失败会怎样 / 应到哪里定位”的答案，使读者能自行检查理解。

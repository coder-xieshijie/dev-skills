# MR 阅读指南

让读者能够解释本次改动的关键行为、判断重要取舍，并找到修改或排查问题的入口。默认交付中文 Markdown；阅读深度由行为与风险决定，正文简洁，证据可下钻。

## 1. 固定分析对象

从当前请求、仓库和已确认讨论确定目标行为、比较范围、读者背景与输出位置。未知业务意图写为假设；可从代码查明的问题直接查明。

- MR/PR：取得项目、目标分支、base/head SHA、diff 是否完整；分清平台 diff base、目标分支 tip 与 merge-base。优先使用已认证的平台 CLI/API，再以固定 SHA 的本地代码补足。
- 本地差异：明确 staged、unstaged、untracked 或指定 commits；工作区未提交时记录快照标识或内容哈希。不要把当前工作区当成远端 head。
- 记录 diff 的生成口径（含上下文行数和重命名检测）；先看变更文件、状态、规模和截断情况，再追关键入口、调用方、实现、数据落点与测试。新增、删除、重命名和配置变化均纳入清单。
- 只有 diff 或部分材料时，标注哪些调用、实现和验证不可见。给出可完成的指南；无法确定对象且没有可用材料时才请求必要输入。

完成条件：读者知道这份指南针对哪个快照、什么需求，以及能证明到哪里。

## 2. 还原行为，选择重点

先用一条正常路径说明“谁触发 → 谁作决定 → 什么状态或外部系统变化 → 谁看到结果”，在相应位置加入本次相关的失败路径。把旧行为与新行为并列；纯重构则指出应保持的行为与改变的内部责任。

以**设计决定或行为变化**组织重点，文件只作为证据。扫描全部变更后，结合后果、影响面、设计新颖度、理解难度和现有证据缺口选择阅读顺序。每个重点说清为什么入选；少量代码改变共享默认值、权限、协议或数据语义时也可能最重要。

全貌清单中的状态用“重点展开 / 简述并映射 / 有依据的豁免 / 未解释”。证据未知但后果重的点保留；与本次无关的维度用一句依据裁剪。优先级是人的阅读顺序，与缺陷严重等级分开。

完成条件：读者知道先看什么、为什么，以及哪些改动暂时没有解释。

## 3. 用三个视角核对同一行为

它们是分析视角，可以交叉；不是要求代码采用三层架构。

- **顶层契约**：用户可见结果、输入与前提、输出与后置条件、失败/重试/取消语义；接口使用者必须知道什么；状态和决策归谁；哪些实现细节被隐藏；已确认的演进与兼容要求。
- **中间逻辑**：入口到结果的控制流、数据流、状态转移，哪一步依赖哪项保证，哪里发生外部副作用。
- **底层约束**：实际分配与释放、容量和工作量、数据读取与写入、并发与提交边界、部分失败与恢复、身份和权限实施位置。

在涉及对应问题时，读取 [design-lenses.md](references/design-lenses.md) 的相关行，用其中的证据要求和反事实问题下钻。设计模式是候选手段；先查现有机制是否已经满足需求，再讨论必要改动。

对每个重点给出“当前选择及原因 / 判断依据 / 一个相关替代方案及代价（确有选择时）/ 代码证据 / 验证方式”。既解释成立的好设计，也解释取舍与缺口。不能从代码推断作者动机时标注“设计效果”或“推断”。

## 4. 按阅读层级展开，并保留语义

采用参考请求中的三档阅读方式：

- **L1 核心**：默认最多 3 个最重要的决定；不够 3 个时按实际数量。每点连到 L2/L3 和关键代码。
- **L2 主链路**：在 L1 上扩展，默认最多 7 个主题，说明协作、状态与异常。额外细节进入 L3；高后果问题即使超出数量也必须在首页提示。
- **L3 细节与全貌**：按主题下钻到伪代码、接口、状态、约束、代码映射、测试和调试入口；全部变更在账本中可查。简单改动可以合并 L2/L3。

这些数量是展示默认值，不是认知定律或风险上限。上层的一个步骤可以在下层展开为多个步骤；每次展开保持同样的前提、结果和副作用语义。

给核心伪代码块稳定 ID（如 P01），给不变量 ID（如 I01）。保留真实状态名、字段名、错误码以及影响行为的条件、顺序、事务范围、等待、取消、清理和权限检查。保留真实返回或抛错行为；未知被调函数写“保证待核实”，建议方案单独标注。

只展开高决策密度逻辑，不逐行翻译语法，不设伪代码行数。若读取版本存在“写入成功、后续通知失败”的窗口，要在伪代码中显示窗口；不能将两步改写成代码并未提供的原子操作。非代码变更用规则或配置语义代替伪代码。

## 5. 双向映射与证据分级

正向：每个 P/I/关键决定 → 文件、符号、行区间、所在快照 commit；附能直接定位的链接。head 新增用新行，base 删除用旧行，重命名列两侧路径。引入该逻辑的 commit 仅在已查历史时填写，不能用 head 冒充引入提交。

反向：每个变更 hunk（diff 中的一块连续变更）都有 ID，映射到一个或多个解释块，或给出具体豁免理由。混合 hunk 中的业务部分仍须解释；必要时细分子范围且保持父 hunk 可对账。

- generated、test、格式、搬移、re-export、type-only 是待核实的分类，不凭文件名自动豁免。生成来源、协议类型、导出路径、配置、迁移和权限声明的语义变化可能是重点。
- 测试正文通常不进入主流程讲解，但需读取断言以判断它证明什么。测试可豁免生产逻辑展开，不能因此忽略测试证据或把未运行的测试写成通过。
- 输出 hunk 总数、已解释、已说明豁免、未解释及清单；按唯一 hunk 计数，不能把多个映射相加。只有完整清单时计算比例；分母为零写“不适用”，截断材料写“部分范围”。映射覆盖与测试覆盖、正确性分开报告。

每条重要主张分别写：**代码事实 / 已确认需求 / 推断 / 未知**；另列验证状态：**静态核实 / 有测试未运行 / 已运行及结果 / 未验证**。两类标签可组合。声称缺陷时给出触发条件、代码证据与后果；证据不足则留作问题。

## 6. 形成指南并核验

参照 [output-template.md](references/output-template.md) 排版；按规模合并空章节。首次使用或不确定如何保持伪代码忠实时，可读 [worked-example.md](references/worked-example.md)。

交付前完成：

- 正常路径和关键失败路径均能从入口走到可见结果；顶层承诺与底层机制不一致处已指出。
- L1/L2 的每个重点均可定位到具体证据，P/I 的实际引用存在且版本一致。
- 全部变更有账，未解释项显式列出。末尾回读 head；发生变化时标注“已过时的固定快照”，更新后重新对账才称最新。
- 提供简短的阅读路线及故障定位入口：观察什么字段/日志，在哪个函数断点，预期与异常分别是什么。启动命令、测试命令从仓库实际配置核实；未运行须注明。
- 用具体场景自检：读者能否说明关键取舍、预测一次相关失败、定位对应代码？写出答案与证据；若不能，补足缺失链路。

默认执行读取与文档生成。运行受影响测试、修改实现、发布评论或批准/合并 MR 等动作沿用用户当前授权。交付指南与验证边界，不把分析自动升级成修改请求或合并结论。

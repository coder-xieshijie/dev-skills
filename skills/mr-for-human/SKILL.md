# MR for Human

让读者能够解释本次改动的关键行为、判断重要取舍，并找到修改或排查问题的入口。默认交付中文 Markdown。

输出是金字塔结构：最核心的内容放最前面，再逐步展开。每一节内部同样先给结论，再给证据。阅读深度由行为与重要性决定，正文简洁，证据可下钻。

## 1. 固定分析对象

从当前请求、仓库和已确认讨论确定目标行为、比较范围、读者背景与输出位置。未知业务意图写为假设；可从代码查明的问题直接查明。

- MR/PR：取得项目、目标分支、base/head SHA、diff 是否完整；分清平台 diff base、目标分支 tip 与 merge-base。优先使用已认证的平台 CLI/API，再以固定 SHA 的本地代码补足。
- 本地差异：明确 staged、unstaged、untracked 或指定 commits；工作区未提交时记录快照标识或内容哈希。不要把当前工作区当成远端 head。
- 记录 diff 的生成口径（含上下文行数和重命名检测）；先看变更文件、状态、规模和截断情况，再追关键入口、调用方、实现、数据落点与测试。新增、删除、重命名和配置变化均纳入清单。
- 只有 diff 或部分材料时，标注哪些调用、实现和验证不可见。给出可完成的指南；无法确定对象且没有可用材料时才请求必要输入。

完成条件：读者知道这份指南针对哪个快照、什么需求，以及能证明到哪里。

## 2. 还原行为，按重要性选择重点

先用一条正常路径说明“谁触发 → 谁作决定 → 什么状态或外部系统变化 → 谁看到结果”，在相应位置加入本次相关的失败路径。把旧行为与新行为并列；纯重构则指出应保持的行为与改变的内部责任。

重点的单位是**实现选择或行为变化**，文件只作为证据。判据是：**改掉它，功能的行为或保证会不会变。**四个方向：

- **承载承诺**：功能对外说的某句话，是靠这段代码兑现的。
- **划定边界**：事务范围、并发范围、信任边界、资源生命周期的起止。边界一旦定下，后面的代码都在它里面运行。
- **被复用**：共享默认值、公共协议、公共工具函数。少量代码改变共享语义时也可能最重要。
- **建立新约束**：新状态、新存储、新的异步边界，之后的代码都要遵守它。

扫描全部变更后再排序。每个重点说清为什么入选，以及为什么排在这个位置。理解难度和证据缺口影响展开方式，不单独构成重要性；证据未知但后果重的点保留。优先级是人的阅读顺序，与缺陷严重等级分开。

完成条件：读者知道先看什么、为什么，以及哪些改动暂时没有展开。

## 3. 三个分析视角

它们是分析视角，可以交叉；不是要求代码采用三层架构。三者对不上的地方，就是最重要的实现事实。

### 3.1 顶层：功能、抽象与契约

- **功能清单**：谁触发，在什么条件下得到什么结果；失败、拒绝、取消分别产生什么结果。
- **抽象清单**：本次涉及的 interface、facade、seam 各自**隐藏了哪个设计决定**，调用者因此可以不知道什么。判断标准不是有没有定义接口，而是哪种实际会发生的变化能被限制在这个边界内。新增包装层若仍泄漏相同细节，只增加导航成本。
- **契约**：输入与前提、输出与后置条件、失败/重试/取消语义；接口使用者必须知道什么；状态和决策归谁；已确认的演进与兼容要求。

### 3.2 中间层：执行逻辑

入口到结果的控制流、数据流、状态转移，哪一步依赖哪项保证，哪里发生外部副作用。按第 4 节的方式拆分并给出核心伪代码。

### 3.3 底层：实现所依赖的运行事实

这一节写的是**这次实现在各维度上做了什么**，不是问题清单。问题是把实现讲清楚之后自然暴露的结论。

默认必查六项，各对应一条绕不过去的事实：

- **资源生命周期**：谁创建、谁释放；异常与取消路径如何结束占用。
- **规模与容量**：工作量由哪些变量决定；是否全量加载、N+1、无界排队、重复扫描。
- **并发一致性**：哪些读写会交错；唯一性或版本检查在哪里生效；锁与事务的实际范围。
- **部分失败**：跨进程、跨系统的步骤在哪些点之间可以独立失败；崩溃或超时后哪些事实已经成立。
- **信任边界**：身份从哪里来；在哪个真实资源操作上检查权限；后台、恢复、重试入口是否同样受控。
- **可观测与恢复**：执行、持久化、通知、展示是否被混成一个状态；丢失的一步如何定位。

触发式维度，本次改动碰到才展开：幂等与重试身份、过载与背压、时间与时钟、缓存一致性、序列化与编码、迁移与部署期、不可逆操作。

每个适用维度按四句写：

1. **这次实现做了什么**：具体的读写、分配、检查，边界划在哪。
2. **它依赖什么成立**：其他组件的保证、数据规模、并发度、外部系统语义。
3. **证据**：文件、符号、行区间。
4. **依赖不成立会怎样**：仅在依赖确实未被证明时写。

维度适用但实现没有问题时，仍然写前三句——“这个维度看过了，工作量是常数”本身就是全貌的一部分。与本次无关的维度用一句依据裁剪。说不出具体依赖条件的疑问不写进第 4 句，放入“待确认”。

在涉及对应问题时，读取 [design-lenses.md](references/design-lenses.md) 的相关行，用其中的证据要求和反事实问题下钻；那张表不是封闭清单，表外的约束按同样四句处理。设计模式是候选手段；先查现有机制是否已经满足需求，再讨论必要改动。

对每个重点给出“当前选择及原因 / 判断依据 / 一个相关替代方案及代价（确有选择时）/ 代码证据 / 验证方式”。既解释成立的好设计，也解释取舍与缺口。不能从代码推断作者动机时标注“设计效果”或“推断”。

## 4. 金字塔表达

**第一屏**：最多 5 条，可以跨三个视角。每条一行，标注类型（明显问题 / 潜在风险 / 核心决定）、一句结论、代码位置，以及**一句为什么排在这个位置**。明显问题无条件进第一屏，不受 5 条限制。

- **明显问题**能构造具体输入或时序，证明结果违反契约或现有系统设计；拿得出反例，读者该改代码。
- **潜在风险**实现自身自洽，但依赖一个尚未证实成立的条件；拿得出触发条件，读者先去确认那个条件。
- 排序按分档，不打分：已证明且后果不可逆 > 已证明且后果可恢复 > 未证实但后果不可逆或不可观测 > 未证实且后果可恢复 > 可维护性。同档内按触发条件有多容易满足排。后果不可观测的往前排，因为出了事没人会知道去修。

**中间层拆分**：先 3 个核心执行决定（不够 3 个按实际数量），再扩展到最多 7 个主题，说明协作、状态与异常。这些数量是展示默认值，不是认知定律或风险上限。上层的一个步骤可以在下层展开为多个步骤；每次展开保持同样的前提、结果和副作用语义。

**核心伪代码**：给伪代码块稳定 ID（如 P01），给不变量 ID（如 I01）。保留真实状态名、字段名、错误码以及影响行为的条件、顺序、事务范围、等待、取消、清理和权限检查。保留真实返回或抛错行为；未知被调函数写“保证待核实”，建议方案单独标注。

只展开高决策密度逻辑，不逐行翻译语法，不设伪代码行数。若读取版本存在“写入成功、后续通知失败”的窗口，要在伪代码中显示窗口；不能将两步改写成代码并未提供的原子操作。非代码变更用规则或配置语义代替伪代码。

## 5. 代码定位与证据分级

**正向映射**：每个 P/I/重点 → 文件、符号、行区间、所在快照 commit；附能直接定位的链接。head 新增用新行，base 删除用旧行，重命名列两侧路径。引入该逻辑的 commit 仅在已查历史时填写，不能用 head 冒充引入提交。伪代码的价值是忠实，不能核对就不如不写，因此这一项不省略。

**未展开的改动**：扫描全部变更后，挑选重点列出没有展开的部分，每条一句话说明为什么次要。下面五类即使判断为次要也必须列出：权限相关、配置与默认值、数据库迁移、协议/IDL 定义、共享工具函数。它们的共同特点是改动行数少但影响面大，正是抓大放小最容易误伤的地方。

本节的保证边界要写明：这是“已扫描全部改动并主动列出被判为次要的高敏感项”，不是“逐块记账、漏了必然被发现”。

- generated、test、格式、搬移、re-export、type-only 是待核实的分类，不凭文件名自动豁免。生成来源、协议类型、导出路径、配置、迁移和权限声明的语义变化可能是重点。
- 测试正文通常不进入主流程讲解，但需读取断言以判断它证明什么。测试可豁免生产逻辑展开，不能因此忽略测试证据或把未运行的测试写成通过。

**证据分级**：每条重要主张分别写**代码事实 / 已确认需求 / 推断 / 未知**；另列验证状态：**静态核实 / 有测试未运行 / 已运行及结果 / 未验证**。两类标签可组合。声称明显问题时给出反例的触发条件、代码证据与后果；只能给出待确认条件的按潜在风险写；两者都给不出的留在“待确认”。

## 6. 形成指南并核验

参照 [output-template.md](references/output-template.md) 排版；按规模合并空章节。首次使用或不确定如何保持伪代码忠实时，可读 [worked-example.md](references/worked-example.md)。

交付前完成：

- 正常路径和关键失败路径均能从入口走到可见结果；顶层承诺与底层机制不一致处已指出。
- 第一屏每条都有代码证据和排序理由；P/I 的实际引用存在且版本一致。
- 底层六项默认维度都有处理结果：展开、或一句依据说明不适用。
- 未展开的改动已列出，五类高敏感类别已逐类核对。末尾回读 head；发生变化时标注“已过时的固定快照”，更新后重新对账才称最新。
- 提供简短的阅读路线及故障定位入口：观察什么字段/日志，在哪个函数断点，预期与异常分别是什么。启动命令、测试命令从仓库实际配置核实；未运行须注明。
- 用具体场景自检：读者能否说明关键取舍、预测一次相关失败、定位对应代码？写出答案与证据；若不能，补足缺失链路。

默认执行读取与文档生成。运行受影响测试、修改实现、发布评论或批准/合并 MR 等动作沿用用户当前授权。交付指南与验证边界，不把分析自动升级成修改请求或合并结论。

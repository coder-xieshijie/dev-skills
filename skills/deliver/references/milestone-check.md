# 里程碑检查说明

写给检查一个里程碑的 subagent。调用方给出：

- spec 和 verify 的路径；
- 这个里程碑对应的场景 ID；
- 这个里程碑的改动范围：起止 commit；
- 这些场景的证据路径。

## 目的

owner 刚做完一段实现，并自己跑通了对应的场景。你在新上下文里对照 spec 检查它，尽早发现问题，免得后面的工作建在坏的基础上。你不做最终判定：最终由另一家模型在单独的 session 中验证。只按 spec、verify、代码和证据判断；owner 在对话、提交信息或 plan.md 里的说法都不作为依据。

## 要做的事

1. **看证据。** 对每个场景，逐个检查点读证据：证据是否读到了检查点要求的实际值或状态，是否来自场景写的入口。证据缺失，或者证明不了检查点，都是问题。
2. **读改动。** 读起止 commit 之间的 diff，对照 spec 找问题，例如：规定的行为只在部分入口实现；默认启动路径没有接上新能力；违反非目标或硬约束；会让本里程碑之外、已经跑通的场景失效。
3. **只检查。** 不改文件，不提交，不启动或停止应用。

## 报告

第一行写你的确切模型 ID，取自你的系统提示词；第二行写你的推理强度，系统提示词里没有写明时写“未写明”：

```text
model: <模型 ID>
effort: <推理强度或“未写明”>
```

之后每条问题写：场景 ID 或文件位置、问题、依据（spec 或 verify 的原文）、影响。只报告会让实现不符合 spec 或让场景判定出错的问题，其他建议最多两条，标为“可选”。没有问题时写“未发现问题”，并列出检查过的场景和文件。

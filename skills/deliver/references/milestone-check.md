# 里程碑检查说明

写给检查一个里程碑的 subagent。每一轮检查分代码和证据两部分，各由一个 subagent 做；调用方写明你做哪一部分，并给出：

- spec 和 verify 的路径；
- 这个里程碑对应的场景 ID；
- 这个里程碑的改动范围：起止 commit，终点是场景所跑的 head；
- 证据部分另给这些场景的证据路径；有场景没在终点重跑的，再给 `select-scenarios.mjs` 对这段改动的输出。

## 目的

owner 刚提交了一段实现。代码部分在 owner 跑场景的同时进行，不等场景结果；证据部分在场景跑完后进行。你在新上下文里对照 spec 检查它，尽早发现问题，免得后面的工作建在坏的基础上。你不做最终判定：最终由另一家模型在单独的 session 中验证。只按 spec、verify、代码和证据判断；owner 在对话、提交信息或 plan.md 里的说法都不作为依据。

## 要做的事

1. **代码部分：读改动。** 读起止 commit 之间的 diff，对照 spec 找问题，例如：规定的行为只在部分入口实现；默认启动路径没有接上新能力；违反非目标或硬约束；会让本里程碑之外、已经跑通的场景失效。不看证据，也不等场景结果。
2. **证据部分：看证据。** 对每个场景，逐个检查点读证据：证据是否读到了检查点要求的实际值或状态，是否来自场景写的入口，是否在范围终点的 commit 上跑出来。在更早的 head 上跑出的，只有 `select-scenarios.mjs` 的输出表明此后的改动不影响这个场景时才算数。证据缺失、不在这个 commit 上又没有这样的输出，或者证明不了检查点，都是问题；verify 列出的覆盖盲区里的检查点除外。
3. **只检查。** 两部分都不改文件，不提交，不启动或停止应用。

## 报告

前两行写你的确切模型 ID（取自你的系统提示词）和你做的部分：

```text
model: <模型 ID>
part: <code|evidence>
```

之后每条问题写：场景 ID 或文件位置、问题、依据（spec 或 verify 的原文）、影响。只报告会让实现不符合 spec 或让场景判定出错的问题，其他建议最多两条，标为“可选”。没有问题时写“未发现问题”，并列出检查过的场景和文件。

# 验证说明

写给独立验证者。调用方用 `run-verifier.mjs` 启动你，在验证输入文件里给出以下内容：

- spec 和 verify 的路径；
- 待验证的 head SHA，以及基线 SHA；
- 验证检出目录；
- 项目验证能力的位置；
- review-rules 的路径；
- 证据目录的路径；
- 允许你使用的环境：给你的实例、profile、端口和数据目录，可用的测试数据，以及结束时要清理的范围。

## 目的

这次改动由另一个 agent 实现，它会自己宣布完成。你的结论决定这个 MR 能不能合入。只按 spec 和 verify 判断；MR 描述、提交信息和 plan.md 里的说法都不能作为依据。

## 要做的事

1. **确认检出。** 检出目录的 `HEAD` 等于给定的 head SHA，并且工作树干净。不满足时停止，并在报告里写明原因。
2. **在运行中的应用上跑场景。** 只在验证输入给出的环境范围内启动和操作应用，不用 owner 或用户正在用的实例。范围内起不来，或者被沙箱、权限挡住时，不自行扩大权限，把受影响的场景标为 UNVERIFIED，说明写“环境受阻”和原因。按项目的验证能力启动应用，执行 verify.md 的冒烟集、每个场景和回归范围。每个场景都从它写的入口操作，按检查点读取实际的值和状态，证据存到证据目录。只看到界面显示、函数被调用或某行日志出现，只能作辅助证据。
3. **对照 spec 审代码。** 读基线到 head 的 diff，按 spec 和 review-rules 判断。只把影响正确性或违反 spec 的情况记为问题，例如：规定的行为没有实现，或只在部分入口实现；默认启动路径没有接上新能力；违反非目标或硬约束；违反 verify 里的机械检查。其他建议最多三条，标为“可选”。
4. **不改动。** 不修改代码、不提交、不推送。结束时停掉你启动的进程，在验证输入给出的清理范围内清理测试数据，证据保留。

## 复验

调用方另外给出上一次验证的 head 和报告时，这次是复验。读上次 head 到本次 head 的 diff，自己判断哪些场景受影响，然后重跑这些场景、冒烟集、回归范围和代码审查。不受影响的场景沿用上次的结果，在说明栏写“沿用 <上次 head 前 12 位>”和不受影响的理由。拿不准的就重跑。上次 FAIL 的场景一律重跑。

## 判定

| 结果 | 条件 |
|---|---|
| PASS | 每个检查点都读到了符合 spec 字面预期的实际值，证据齐全 |
| FAIL | 任一检查点不符合，或者出现了“不得出现”的结果 |
| UNVERIFIED | 工具或环境无法执行或观察。写明原因，并区分是 verify 列出的覆盖盲区，还是环境问题 |

没有实际执行的场景不能写 PASS。

## 报告格式

报告作为你的最终回复输出，调用方原样保存为报告文件。`scripts/run-verifier.mjs` 和 `scripts/check-delivery.mjs` 会读取 `head:` 行、`验证模型：` 行和场景表，这三部分格式固定：

```text
head: <40 位 SHA>
base: <SHA>
验证模型：<CLI 与模型>
检出：HEAD 与给定 SHA 一致，工作树干净

| 场景 | 结果 | 证据 | 说明 |
|---|---|---|---|
| S01 | PASS | <证据路径> | |
| S02 | FAIL | <证据路径> | 检查点 2：预期 3，实际 4 |
```

verify.md 的每个场景在表里占一行。表后依次写：

- **冒烟集与回归范围**：结果和证据。
- **代码问题**：每条写位置、问题、违反的 spec 条款或准则、触发条件与后果。
- **可选建议**：最多三条。

这几部分没有内容时写“无”，不要省略：`run-verifier.mjs` 和 `check-delivery.mjs` 用它们判断报告是否完整。场景表每行四列，PASS 和 FAIL 的证据列不能为空。

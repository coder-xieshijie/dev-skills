# plan.md 格式

依据 OpenAI 的 ExecPlan（[Using PLANS.md for multi-hour problem solving](https://cookbook.openai.com/articles/codex_exec_plans)），按本流程做了调整。plan.md 由 owner 写，边做边改。它的读者是中断后接手的新 session：只读 plan.md 和 git 历史，就要能接着做。

## 与 ExecPlan 原文的不同

- 原文要求计划完全自包含。这里 spec.md、verify.md 已冻结，并且和 plan.md 在同一目录，所以 plan.md 引用它们，不复述需求和场景。原文也允许引用已提交的前序文档。
- 验收以 verify.md 的场景为准，plan.md 不重新定义。plan.md 只写场景和里程碑的对应关系，以及“实现后绑定命令”的实际命令。
- 新增“冻结输入”一节，供机械检查使用。

## 各节

按下面的顺序写。标“持续更新”的四节，每次停下时都要更新；其余各节在改变做法时更新，同时在决策日志里写原因。改变做法时，所有受影响的节一起改，不只在末尾追加。

### 冻结输入

格式固定，`scripts/check-delivery.mjs` 读取前两行；路径相对于 plan.md 所在目录：

```text
- spec: spec.md sha256=<64 位十六进制>
- verify: verify.md sha256=<64 位十六进制>
- 基线: <分支> @ <commit>
```

### 目的

一两句：完成后用户能做什么，怎样看到它生效。取自 spec 的目的。

### 进度（持续更新）

带时间的勾选列表，每步一行：时间、做了什么、跑通了哪些场景、commit。每次停下都要记；没做完的写成“已完成 X；剩余 Y”。

```text
- [x] (2026-09-29 14:05+08:00) M1 补额度只读查询；S01 跑通；a1b2c3d
- [ ] M2 用尽边界（已完成：界面入口 S02；剩余：命令行入口 S03）
```

### 意外与发现（持续更新）

和预想不同、影响了做法的事实，例如库不支持、接口行为不同、性能不够。每条写现象和简短证据。普通 bug 修好了只记进度，不记这里。

### 决策日志（持续更新）

每个自主决定和每次改变做法：决定、原因、日期。MR 里的“自主决定”从这里汇总。

### 结果与复盘（持续更新）

里程碑完成和全部完成时写：做成了什么，还缺什么，和目的对照的结果，以及这次暴露的仓库缺口，比如缺什么验证能力、文档或 lint。仓库缺口留给之后补进仓库。

### 现状与上下文

假设读者对仓库一无所知：相关的文件和模块（写完整路径）、它们怎样配合，以及要用到的术语。

### 里程碑

每个里程碑写一段：范围，完成后多了什么，对应 verify 的哪些场景，要跑哪些质量命令。验证工具缺口排在最前面。每个里程碑都能单独验证。

### 验证与验收

怎样启动应用、怎样跑冒烟集；每个场景怎样从入口驱动（引用项目的验证能力）；“实现后绑定命令”的场景写出实际命令。判定以 verify.md 的检查点为准。

### 幂等与恢复

哪些步骤可以重复执行；有风险的步骤怎样重试或回退；结束后怎样清理环境。

### 接口与依赖

用到的库、模块和服务，以及为什么用；做完时必须存在的类型、接口和函数签名。spec 没有规定的部分是 owner 的选择，做法变了可以改。

## 大小

证据只写路径和一句结论，完整输出放在 `evidence/`。进度长到每次开工读 plan.md 都费时的时候，可以把进度移到同目录的 `progress.md`，plan.md 里留一个链接；冻结输入仍留在 plan.md。OpenAI 的长任务实践也把计划和状态分成两个文件（Plan.md 和 Documentation.md）。
